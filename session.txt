INVESTIGATION FINDINGS (this session)
  - PerCpuAccessReady is set ONLY in SMP.c:267 (FinalizeMonoProcessorMode) and
    SMP.c:337 (InitializeBspCpuRecord). Both run AFTER LoadAllDrivers/
    InitializeKernel drivers load. So at GrowDescriptorSlab time (driver[2]
    load, T0) PerCpuAccessReady == FALSE -> GetCurrentTask takes the pre-SMP
    fallback (RunQueues[0], no CurrentCPU/GS read). => The x86-64 GS=0 fault
    (T20) and the GrowDescriptorSlab hang are NOT the same root cause.
  - The GrowDescriptorSlab hang (Step 5 only) is between the `phys=` DEBUG
    log and the missing `FindFreeRegion` DEBUG log => inside
    AllocKernelRegion -> AllocRegionForProcess, almost certainly at/around
    LockMutex(MUTEX_MEMORY, INFINITY) (Mutex.c:244..) OR ValidatePhysicalTargetRange.
    LockMutex sleeps in a FOREVER loop (`IdleCPU(); DisableInterrupts();`) gated on
    Mutex->Task being released by its owner; at T0 GetSystemTime does not advance
    (interrupts/timer not enabled until EnableInterrupts at T10) => a held-but-not-
    released MUTEX_MEMORY would hang forever. Need a backtrace to confirm location.
  - On the PREVIOUS machine the Step-5 first-free page was 0x7FC3000 (top of
    128 MB RAM); on THIS machine it is 0x48D000 (low). The addresses differ per
    machine, so the hang is NOT simply a last-page/top-of-RAM edge case — it
    reproduces at different physical pages, pointing to a logic/ordering defect
    in how Step 5 interacts with the memory driver init, not raw layout.
  - Step 4 (no Step 5) does NOT hang at GrowDescriptorSlab on either machine;
    Step 5 alone triggers it. So it is genuinely causally linked to the Step 5
    changes. The 34 KB RunQueues[32] .data growth is insufficient to explain a
    low-page (0x48D000) vs top-page (0x7FC3000) flip; the defect is logical.
